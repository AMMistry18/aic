# Native survey motion — implementation plan

Status: **plan only, nothing built.** Written 2026-07-28 after the staged-SFP
coverage/occlusion fix (`CHECK_BOARD_VISIBILITY_V4_HANDOFF.md` §23).

## 1. What this changes and why it is worth it

Today the skill selects a six-joint branch, validates it, throws it away, and
publishes a **Cartesian** TCP pose. Move Robot re-solves that pose and may take
any co-terminal branch (handoff §11). Three consequences, all of them live:

| Symptom | Root cause |
| --- | --- |
| "the arm contorts and gets between the cameras and the board" | the executed branch is not the validated one |
| arm-in-view / self-clearance are guarantees with holes | §7.1: cannot cover a branch outside `solve_ranked`'s set |
| 1193-point, 29.44 s transits for a 0.374 m move | the planner's path is not ours and is not inspected |

Native motion fixes all three by the same mechanism, and the mechanism is worth
stating precisely because it is the whole argument:

> **If we choose the path, the path becomes computable — and therefore
> checkable.** A Cartesian endpoint can only be validated at its endpoint. A
> joint-space min-jerk segment from a known start to a chosen target has a closed
> form, so every link can be swept along it offline, in the sweep harness, before
> the arm moves.

That is also why `sampled_cartesian_path_is_safe()` has sat unused in
`board_stage2.py`: there was never a path to hand it.

**The honest cost:** we give up Move Robot's workcell collision model, which has
real meshes. §2 is about earning that back. Do not start §4 before §2 is
credible — publishing a pose the planner would have refused is a hard failure,
and the standing instruction on collisions is absolute.

**This is not a repeat of §20.** Three Stage-1 acquisition designs failed and were
deleted. Every one of them was *open-loop about where the board was* — they
nudged and re-measured, so they could only hill-climb and had no gradient when the
insignia left frame. This moves to a **pose computed from a board hypothesis the
skill already has**, with a fixed target, a validated path and no feedback loop to
diverge. Different problem. Keep it that way: if anyone proposes servoing here,
re-read §20 first.

## 2. Phase 0 — de-risk the controller (blocking, hardware)

**Nothing else in this plan matters if joint target mode will not hold.** §20
item 2 records the measured failure: the deployed controller dropped joint target
mode **0.43 s into** a move — `controller left joint target mode; joint target
reversed` — and the conclusion drawn was "the joint-target path is not
dependable."

Do not accept that conclusion yet; it was a single observation and the acquisition
code around it had a separate deadline bug that has since been fixed. What is
already hardened: `_request_target_mode()` treats the **reported** mode on
`controller_state` as the acceptance criterion rather than the service response,
retries at least four times, and publishes a measured-state hold command after two
failures to flush a blocking in-flight execution. The gap is not *acquiring* the
mode, it is *keeping* it.

Investigate, in this order:

1. Log every `controller_state` mode transition at full rate through a small
   single-joint move (5-10°, one joint, well inside limits). Timestamp against
   each published joint command.
2. Correlate the drop against the obvious candidates: publish rate
   (`publish_hz`), the first command after the switch, a controller-side watchdog
   on command staleness, an in-flight Cartesian execution not yet complete, or
   another node publishing to `/aic_controller/pose_commands` concurrently.
3. Deliverable: a reproducible statement of the precondition, e.g. "mode is
   dropped if no joint command arrives within X ms" or "mode is dropped by any
   pose_command publication."

**Design the fallback in this phase, not later.** If joint mode cannot be held,
most of the benefit is still reachable without it: keep streaming Cartesian
`move_smooth()`, but stream a **dense sequence of TCP poses generated by forward
kinematics along the joint-validated path**. The controller's own IK tracks a path
that never leaves the validated corridor, so branch drift is bounded by waypoint
spacing rather than left to the planner. It is strictly weaker than joint mode —
the controller still picks windings between waypoints — but it is inspectable and
it needs no mode change at all.

Exit criterion for Phase 0: either a held joint mode over a 90° move, or a
committed decision to use the dense-Cartesian fallback.

## 3. Phase 1 — a collision model worth trusting

### 3.1 What exists today

Only three things, and none is an environment model:

- `UR5eArm.self_clearance()` — flange probes vs the **forearm centreline** only,
  140 mm.
- `UR5eArm.link_segments()` — **two** capsules: upper arm (60 mm radius) and
  forearm (50 mm). Not the base, shoulder, wrist links, or the tool.
- workspace scalars in `search_survey_pose`: base-link Z ≥ 0.02 m, base-origin
  norm ≤ 1.20 m, board-normal clearance ≥ 0.2393 m.

### 3.2 Build

1. **Extend `link_segments` to the full chain** — all six links plus the tool
   capsule, with radii from `ur_gz.urdf.xacro`. This also strengthens the
   arm-in-view gate, which today can only see two links.
2. **Static obstacles.** The geometry is all in-repo, which is what makes this
   tractable — derive from the same source the simulator uses rather than
   re-measuring:
   - `aic_description/urdf/task_board.urdf.xacro` — plate and component origins;
   - `aic_assets/models/*/[component]_macro.xacro` — per-component collision
     boxes (NIC card fins are the tall ones, 0.1793 m above the board);
   - `aic_description/urdf/ur_gz.urdf.xacro` — arm link radii, pedestal, camera
     mount;
   - table plane and fence planes from the cell layout.
   Express board-mounted geometry **in the board frame** so it follows the PnP
   estimate, exactly as the sector boxes already do. Nothing here may become a
   fixed world offset (§17 item 4).
3. **The cables are not modelled, and cannot be.** This closes handoff §22.9
   item 4: the five `sfp_sc_cable` pick objects are spawned from **launch
   arguments** (`cable_x/y/z/roll/pitch/yaw` in
   `aic_bringup/launch/aic_gz_bringup.launch.py`), one at a time — there is no
   authoritative staged pose in any model file. Treat the entire module-strip
   volume as occupied rather than pretending to know where each cable is. The
   survey pose sits 0.80 m above it, so this costs nothing here; it matters for
   any future approach move.
4. **Swept check in joint space.** For N interpolated configurations along the
   path, capsule-vs-box and capsule-vs-plane distance for every link, against a
   margin. Mirror the shape of `sampled_cartesian_path_is_safe()` — same
   monotone-retreat idea, joint space instead of Cartesian.

### 3.3 Validate against the real planner — the part that must not be skipped

Our model is more permissive than reality until proven otherwise. The acceptance
test is agreement, not self-consistency:

> Run our checker and Move Robot's planner over the whole 144-case sweep. Every
> configuration our checker accepts, the planner must also accept. Any
> disagreement is a bug in our model until explained.

This is also the cheapest route to a question that has been open for two sessions:
the **140 mm wrist-camera keep-out**. It was calibrated from a single planner
rejection whose best branch sat at 111 mm, measured to a capsule *centreline*
(~90 mm real surface clearance), and it is now the dominant gate — the 18:07 trace
reads `camera_keepout=61` of 68 probes, i.e. it refuses 90% of reachable framed
poses and so limits how good a branch the search can even choose. With a
mesh-comparable model, 140 mm stops being a guess (§21.3, §22.9 item 5).

## 4. Phase 2 — the force model

### 4.1 State it plainly: there is no enforceable force limit today

The wrist FTS is **raw and untared** (§19.3). Free-space magnitude sweeps
13.6-25.7 N purely with wrist orientation, so:

- `contact_force_n()` reports only force **above** `STATIC_FORCE_ENVELOPE_HI_N =
  27 N`;
- a caller-supplied `max_force_n` below that envelope is **deliberately
  ignored**, because on an untared sensor it reports which way the wrist points;
- so the shipped 18 N default enforces nothing, and the smallest contact the
  skill can currently detect is ~5 N *on top of* a 27 N envelope.

If the competition penalty threshold is anywhere below ~30 N, **the skill cannot
currently respect it.** This is a prerequisite, not a refinement.

### 4.2 Gravity compensation

Model `F = b + R·g` — constant sensor bias `b` (3 unknowns) plus tool weight `g`
(3 unknowns) rotating in the sensor frame. Six unknowns, linear least squares.

Data collection is nearly free: the skill already resolves `base_T_tcp` at every
snapshot, so every force sample can be orientation-tagged. Collect over a slow
sweep of wrist orientations (a dedicated calibration routine, or opportunistically
across runs), solve, and persist the fit.

Then `residual = ‖F − (b + R·g)‖` is a real contact force, and:

- a 5 N or 10 N budget becomes enforceable;
- the guard changes from "magnitude above an envelope" to "residual against the
  predicted static wrench", checked every control tick;
- `STATIC_FORCE_ENVELOPE_HI_N` and the 45 N runaway backstop stay as a
  belt-and-braces fallback for when the fit is unavailable or stale.

§19.3 already names this as the right next step and notes the data is there. It
also warns to **always log the unexplained component next to the raw magnitude** —
a bare "25.72 N" reads as alarming and is in fact free space.

### 4.3 Budget, not just abort

"Never exceed the max" needs three behaviours, not one:

1. **Refuse** before moving if the residual is already near budget.
2. **Abort and retreat** during motion on budget breach — `move_joint_target`
   already reverses to the joint vector saved at transaction start, which is the
   right primitive.
3. **Report** peak residual force in the result, so the force penalty is
   observable per run rather than inferred after scoring.

**Open question for you:** what is the actual maximum, and is it a peak or an
integral/impulse? A peak limit and an impulse limit imply different motion
profiles — a peak limit is satisfied by slowing down, an impulse limit is not.
I have assumed peak. Tell me the number and I will size the guard to it.

## 5. Phase 3 — native execution

Reuse `RobotMotion.move_joint_target()`. It already does most of this, built for
the deleted deterministic Stage 1 and never removed:

- switches to joint mode and **always restores Cartesian** via its `finish()`
  wrapper, including on every failure path;
- quintic min-jerk profile, 0.20 rad/s cap;
- force guard evaluated inside the streaming loop via `stop_requested()`;
- reversal to the complete measured start vector on force, cancellation, stale
  feedback, mode change, or settle-timeout;
- settle detection on measured joints plus TCP speed.

Add:

1. **Pre-flight path validation.** Run the Phase 1 swept check over the whole
   interpolated path and refuse before commanding anything. This is the
   `done=false` path, not an exception.
2. **Monotone per-joint interpolation**, so no joint reverses direction mid-move
   and the executed motion is exactly the validated one.
3. **Segmentation — this is what actually kills the contortion.** A single
   simultaneous swing of three joints through 170° is the reported failure. Where
   the worst-joint delta exceeds a bound, insert via-configurations with a
   deliberate shape: retreat along the board normal, then rotate, then descend.
   Each segment is separately validated and separately force-guarded. Note that
   no *cap* can achieve this — the 18:07 run published `total=363.7°` under a
   passing 400° cap (§23.7) — and no endpoint *ranking* can either, which
   §23.7b measured and rejected. Segmentation is the only lever that acts on the
   path.
4. **Deadline sized from the segment**, not a fixed 6 s. §20 item 2's first bug:
   a 33° segment needs 5.4 s at the 0.20 rad/s cap, and the budget also had to
   absorb up to 2 s of mode-switch retry.
5. **Result fields**: executed joint target, per-segment peak residual force,
   validated-path flag. Keep `result.target` populated with the same Cartesian
   pose for backward compatibility so the existing Flowstate packer does not
   break on day one.

## 6. Phase 4 — Flowstate rewiring

The survey Move Robot step disappears. Two things get *more* important, not less:

- **§18 item 1 is now blocking.** The skill holds the AIC controller session for
  the whole move, so an exception before `Switch To Default Controller` wedges the
  bridge harder than it does today. Put the controller switch in an always-run BT
  branch, or return `success=False` instead of raising. This is already the top
  open item and native motion raises its cost.
- The `success && done && target_valid` gate (§18 item 2) still has to exist,
  because a refused path must not be read as a completed move.

## 7. Sequencing

```
Phase 0  controller de-risk        HARDWARE, BLOCKING   -- can invalidate the approach
Phase 1  collision model          offline, independent  -- gated by planner agreement
Phase 2  force model              offline, independent  -- needs the max-force number
Phase 3  native execution         needs 0, 1, 2
Phase 4  Flowstate rewiring       needs 3
```

Phases 1 and 2 are independent of each other and of Phase 0, so they can proceed
in parallel. **Start Phase 0 first anyway** — it is the only one that can tell us
the plan is wrong.

## 8. Offline validation

Extend both sweep runners from endpoints to **paths**: for all 144 cases, validate
the full interpolated trajectory, not just the selected pose. Report worst link
clearance along the path alongside the existing seat and clearance numbers.

Also fix what §23.9 item 3 flags now, before any of this lands: the SFP harness can
no longer reproduce either shipped regression, because the seat gate fixes them
from inside. Add `--no-seat-gate`. A harness that cannot fail cannot certify.

## 9. Risks, ranked

1. **Joint mode will not hold** (§20 item 2, measured). Mitigation: Phase 0 and a
   designed dense-Cartesian fallback.
2. **Our collision model is more permissive than the planner's.** Mitigation: the
   agreement test in §3.3. Do not ship on self-consistency.
3. **Force sensing stays coarse** if the `b`/`g` fit is unstable — note
   `autocalibrate()` already shows tool offsets varying 197.1 / 200.4 / 201.1 mm
   between runs (§18 item 5), and the same instability would hit `g`.
4. **We own motion failures now.** Today a bad transit is Move Robot's problem;
   afterwards it is ours, in a skill that holds the controller lease.
5. **Arm-in-view is still unvalidated on hardware** (§7). Native motion makes it
   enforceable but does not make it verified.
